# Parsing

#### Basic Concepts 
- Parsing is the process of converting a stream of lexical tokens into an abstract syntax tree representation of a programme by matching it against a grammar for the language
- Parsing is done after lexical analysis in the compiler/interpreter tool chain 
- There are many different approaches to parsing, two common ones:
	- Top down or recursive descent:
		- Builds parse tree from the root down 
		- LL Grammars (reads Left to Right, forms Leftmost derivations)
	- Bottom up
		- Builds parse tree from leaves up
		- LR Parsers (reads Left to Right, forms Rightmost derivations)
		- More complicated but handles a wider range of grammars than LL parsing

#### SHIFT and REDUCE
- The most common approach to implementing LR parsers is to use shift-reduce parsing 
- Token stream is scanned and a forest of partial parsing sub-trees are built form the bottom up
- At each stage the parser can either:
	- Shift -> read the next input token (a new single node parse sub-tree)
	- Reduce -> apply a completed grammar rule to join sub-trees to make a large sub-tree
- Continues until input empty and a single parse tree is formed 
- These act like state machines with actions ERROR, SHIFT, REDUCE, STOP
- Conflicts occurs when the state machine is non-deterministic, i.e. two or more actions can apply.

#### Parser Generators 
- Software tool, given input that describes the rules of your grammar and what actions to perform when each rule is used, will generate code for you that performs parsing.
- We use Happy 

#### Happy 
- Generates Haskell code with a function named of your choosing of type [Token]  -> T where Token and T are both user-definable
- Directives:
	- The name directive %name
		- This specifies the name of the generated parse function 
	- Token type Directive %tokentype
		- Specifies the type of the tokens on the input stream. Defined in the lexer input file
	- Error directive %error
		- Specifies the name of a function of your choosing that will be called when a parsing error occurs. This allows you to customise the error message.
			- This type should be [Token] -> a

- The typical use of actions is to build an abstract syntax tree
- Parsers generated by Happy have a single entry point. This means that the parser will try to match against a single specific non-terminal
	- This is determined by the order the non-terminals are listed in the file - in particular, the first non-terminal listed is the entry point to the grammar 

#### Token Directives
- The tokens themselves are specified using the %token directive 
- The tokens can be given a convenient name for use as terminals in the grammar 
- Use two $ to represent the value of a token matched in the grammar 
- Use _ to act as a wildcard for matching arguments to tokens that you don't need to further use 

#### Returning other datatypes
- The return type of grammar actions does not have to be an AST - you can return any Haskell value 
- You can even evaluate as you parse 
	- This does not construct an AST but instead calculates an Integral value 
	- Note that all actions must have the same type 
- Note the indexing used to select the correct value from the matched token.
